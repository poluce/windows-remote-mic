# HID 按键协议（RC003）

> 对象：RC003 / 小米蓝牙语音遥控器 2 Pro 的按键编码与 HID 通路。
> 可信度：✅ 实证 / ⚠️ 社区/推断 / ❓ 未验证。

---

## 1. 按键通道

RC003 的按键通过蓝牙 HID 键盘报告上报，usage page = `0x07`（Keyboard）。

语音流不经过 HID，走 ATVV（见 `ATVV-协议.md`）。

## 3. Windows 通路差异

| 按键 | Raw Input | WH_KEYBOARD_LL | HOGP 驱动层 |
| --- | --- | --- | --- |
| 上/下/左/右/确定/主页/菜单/电源 | ✅ | ✅ | ✅ |
| 返回 `0xF1`、音量 `0x80/0x81`、TV `0x35` | ❌ | ❌ | ✅ |
| 麦克风 `0x3E` | 部分条件下 | — | ✅ |

- 返回/音量/TV 在 Windows 上被 HOGP 层从键盘输入通道分流，Raw Input 和低级键盘钩子收不到。
- 系统仍会原生处理这些键（返回 → 浏览器后退、TV → 媒体选择、音量 → 系统音量，走 WM_APPCOMMAND）。
- 若要在应用层捕获这些键，需要在 HOGP 驱动层拦截。

### 3.1 注入侧翻译原则（目标设备为准）

识别和注入属于两套不同的 HID 命名空间，**不要直接把遥控器的 usage 抄给虚拟设备**：

- 遥控器的 usage（如音量+ `0x80`）只用于**识别物理按键**——遥控器自己的报告描述符声明了这些 usage，
  所以系统认得它；这不代表我们的虚拟设备也能发同样的值；
- 注入必须翻译成**目标设备声明过的 usage / 页**，或改用 Win32 原语：
  - 虚拟键盘是标准 Boot Keyboard，描述符声明 usage `0x00–0x65`（`KEYBOARD_USAGE_MAX`）；
    超出的 usage 会被 Windows HID 栈**静默丢弃**（无报错、无效果）；
  - 媒体键 / 系统音量键走 Consumer 页（`0x0C`）：Play/Pause `0xCD`、
    Volume Increment/Decrement/Mute `0xE9/0xEA/0xE2`，由独立的虚拟媒体键设备发送；
- 代码侧已有约束：`KeyboardState::add_key` 对越界 usage 直接返回错误（不再静默提交）；
  单测锁定「描述符上限 == 校验常量」且音量 token 不进入键盘设备。
- 历史回归（v0.2.0 起）：音量 +/−/静音被原样注入键盘页 `0x7F/0x80/0x81`，超出 Boot Keyboard
  声明范围 → 日志显示「已执行」但系统音量不动；本次修复改为走 Consumer 页。

## 4. 语音键固件差异

- RC003 语音键多数固件编码为 `0x3E`（键盘 F5）。
- 有实现观察到 RC003-MS 固件为 KEY_F5；另有环境观察到 KEY_F9。
- RC003 的 ATVV Control 通道未观察到 `MIC_BUTTON (0x08)` 事件，语音键的按下/松开主要体现在 HID 键与 ATVV 音频流状态上。
