# 多语音识别方案（VoiceTarget）设计

> 目标：让 RC003 遥控器麦克风键不只服务 Windows 自带语音输入（Win+H），
> 还能一键唤起微信输入法 / 豆包输入法 / 搜狗输入法（以及未来的本地/云 ASR）。
>
> **状态：方案 A（全局 VoiceTarget 运行时分发）已按「先做架构支持」落地（2026-09）。**
> 默认目标仍是 Windows 语音（行为与落地前一致，可直接验证不回归）；
> 第三方输入法（微信/豆包/搜狗）在架构上已支持（枚举/配置/分发/命令/前端下拉
> 全部就位并持久化），**唤起热键与按住说话语义待真机验证后逐个接入**，接入时
> 只需在 `core-input` 补充对应实现，映射/调度/前端无需再改。

---

## 1. 现状盘点

### 音频通路（与识别方案无关，已解耦）

```
BLE GATT Audio → core-atvv 解码(IMA ADPCM→PCM) → core-voice 桥
                → core_audio::sink::AudioSink → 虚拟声卡 CABLE Input
```

- 出口固定为 `CABLE Input`（`ConnectionPage` 里写死 `outputDevice: "CABLE Input"`）。
- 任何能把「虚拟麦克风（CABLE Output）」选作输入的识别服务，都能收到这份音频。
- **这一层不需要为「换识别方案」而改动**——它服务的是“把遥控器语音变成系统级麦克风输入”。

### 触发 / 动作层（现在与 Win+H 强耦合）

| 位置 | 现状 |
| --- | --- |
| `core-mapping` `ActionKind::Voice` | 无参数的裸动作 |
| `core-dispatch` `execute_action` | `A::Voice => core_input::open_voice_typing()`（写死 Win+H） |
| `core-input::open_voice_typing` | 固定 `press_win_h()` |
| `core-input::hotkey` | `token_to_vk` 已支持 win/h/ctrl/alt/space/tab 等；**没有 PTT「按住说话/松开停止」原语**，只有一次性 combo |
| 配置 `config.json` | 只有 `mapping`/`long_press_ms`/`double_click_ms` 等，**无 voice_target** |
| Tauri 命令 | `trigger_voice_typing` 只做 Win+H |
| 前端连接页 | 识别方案下拉已占位（`windows_voice` ready / `ime_wechat`/`ime_doubao`/`ime_sogou` preview），但选中第三方后不生效 |

结论：**音频层已经“可插拔”，缺的是“把 Voice 动作路由到不同识别目标”的配置与执行层。**

## 2. 需求界定（先划清边界）

先明确本阶段要支持什么：

1. **遥控器麦克风键唤起某一种“识别服务”**：本质是往当前前台输入框注入一次
   「打开语音输入」的动作。Windows 语音条、微信/豆包/搜狗输入法都提供这类入口，
   但**触发方式与“按住说话/开关”语义各不相同**。
2. **同一时刻一个目标**：不需要同时开两个语音输入。连接页选一个，全局生效。
3. **映射动作与目标解耦**：映射表仍只表达「麦克风键 → 语音动作」，具体唤起谁
   由全局 `voice_target` 决定（放连接页设置，不放映射页——它是系统级偏好）。
4. **兼容旧配置**：默认 `windows_voice`，旧 `config.json` 无该字段时按 Win+H 行为。

非目标（本阶段不做）：
- 应用内离线 ASR（Whisper 等）直接上屏 —— 需要新音频消费点 + 文本注入路径，
  属另一工程，本方案只在结构上为其留扩展位。
- 同时支持多目标 / 自动切换。

## 3. 可选方案

### 方案 A：Voice 动作保持无参，全局 VoiceTarget 运行时下发
- `ActionKind::Voice` 不变；调度器执行时读一个 `voice_target`（枚举），
  把具体“唤起动作”下发给 `core-input` 的一个可扩展执行器。
- `voice_target` 存 `config.json`；调度器/执行器持有当前值（可热更新）。
- 优点：映射表/旧配置完全不动；语义清晰（映射=按键→语音，配置=语音→哪个服务）。
- 缺点：`core-dispatch` 需要能拿到 voice_target（要在 AppState 里接线）。

### 方案 B：把 Voice 扩展为 `Voice { target: VoiceTarget }` 动作参数
- 每个绑定的动作自带目标（类似 `KeyCombo(Vec<String>)` / `OpenApp(String)`）。
- 优点：粒度最细——不同按键可唤起不同服务。
- 缺点：映射页每个语音动作都要选目标，UI 变重；且“默认麦克风键=语音”
  与“全局用哪个输入法”两处概念重复，容易打架。作为**进阶能力**而非默认形态。

### 方案 C：完全靠通用 KeyCombo / OpenApp 组合
- 不加任何新概念：用户把麦克风键映射成 `KeyCombo([...])` 或 `OpenApp(...)`。
- 优点：零新代码，现在就能做。
- 缺点：热键要用户自己查自己填；无法表达 PTT（按住说话/松开停止）等时序语义；
  不同输入法的“开启/停止”不能可靠统一。仅作逃生通道，不作产品形态。

**结论：主推方案 A，预留方案 B 的扩展位。**
理由：与现有「连接页选识别目标」占位吻合；改动集中、向后兼容；
把“每次按键要知道目标”下沉为“系统当前知道目标”，最贴合单遥控器单语音的用法。

## 5. 架构改动设计（方案 A）

### 5.1 core-mapping：新增 VoiceTarget（纯数据）

```rust
//! crates/core-mapping/src/lib.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum VoiceTarget {
    WindowsVoice, // 默认，向后兼容（缺省时等价于此）
    ImeWechat,
    ImeDoubao,
    ImeSogou,
}

impl Default for VoiceTarget { fn default() -> Self { Self::WindowsVoice } }
```

- `Config` 增加 `#[serde(default)] pub voice_target: VoiceTarget`（`core-config`），
  旧配置反序列化自动落到 `WindowsVoice`。
- 为未来 ASR 预留 `asr_internal`，本阶段不加入枚举，避免半成品选项。

### 5.2 core-input：可扩展的「语音输入控制器」

把现在写死的 Win+H 提为**按 target 分发**，并引入 PTT 语义：

```rust
// 核心抽象（示意）
pub enum VoiceActivation {
    Tap,      // 单次热键：按下触发一次开启（Win+H 等）
    HoldTalk, // 按住说话：Press=按下热键 / Release=松开热键
}

pub fn trigger_voice(target: VoiceTarget) -> Result<()>;
pub fn voice_press(target: VoiceTarget)  -> Result<()>; // PTT 按下边沿
pub fn voice_release(target: VoiceTarget) -> Result<()>; // PTT 松开边沿
```

- Windows Voice：`Tap` → 仍是 `press_win_h()`；`voice_press/release` 与
  「Press/Release → Win+H」语义一致（按住开启会话、松开停止）。
- 第三方目标：先实现 `Tap`/`HoldTalk` 的框架与组合注入；具体热键经真机验证后填入。
- `send_key_combo` 已够支撑大部分热键；若某输入法只接受“按住某键期间持续说”，
  需要 `SendInput` 保持按下 → 计时 → 释放的原语（现有 `hotkey.rs` 每次都是按→放）。

### 5.3 core-dispatch：Voice 动作不再写死 Win+H

`execute_action` 里 `A::Voice` 的执行，从「调 `open_voice_typing`」改为
「经一个可注入的 voice 执行出口（回调/状态）按当前 target 触发」，
与 `AppEvent`/快捷菜单的现有“调度器→壳”模式对齐：

- 调度器新增一个 `voice_trigger: Arc<dyn Fn(...)>` 槽位（类似 `app_event`）；
- Tauri 壳（`src-tauri`）启动时把“读当前 voice_target → 调 core-input”的闭包
  装进去。这样调度器保持对“识别方案”零知识，只表达“这是语音动作”。

### 5.4 配置与 Tauri 命令

- `Config.voice_target: VoiceTarget`，默认 `WindowsVoice`。
- 新命令（放在 `src-tauri/src/commands/connection.rs`，与识别方案/连接设置同域）：
  - `get_voice_target() -> String`（snake_case，如 `windows_voice`）
  - `set_voice_target(target: String)` → 写配置 + 热更新调度器。
- `trigger_voice_typing` 保留（引导页“唤出 Windows 语音输入条、配置 CABLE Output”
  是 Windows 目标的首次配置流程，仍按 Win+H 直调，不随 target 分发）。

### 5.5 前端

- 连接页「识别方案」下拉已就位：
  - `windows_voice`：现有 UI（虚拟声卡/首次配置 CABLE/模拟语音链）保持不变；
  - `ime_*`：选第三方后显示「语音目标 = 微信输入法」状态与对应指引/按钮
    （「唤出微信输入法语音」），模拟语音链仍可跑（验证音频通路），
    但“唤出”按钮调后端新分发命令。
  - 选中值持久化到 `config.json`，刷新/重启后保留。
- 引导页 / 语音说明文案：把「Win+H」相关文字参数化，
  按 target 显示对应入口（至少不出现误导性“Win+H”字样）。
- 映射页：
  - `voice` 动作分类仍叫「语音输入」；label 按当前 target 动态显示
    （例如选微信输入法后显示「语音输入（微信输入法）」），不强制用户重配映射。
  - 方案 B 预留：将来若要做“每键不同目标”，再把 `VoiceTarget` 加进向导高级选项。

### 5.6 兼容性 / 迁移

- 旧配置无 `voice_target` → 反序列化默认 `WindowsVoice` → 行为与今天完全一致。
- 映射表里的 `ActionKind::Voice` 无参 → 无需迁移。
- `rc003_hid_tap.js`/HOGP 旁路与识别方案无关，不动。

## 7. 已拍板的决策（2026-09）

1. **第三方目标范围**：微信/豆包/搜狗三个都作为 `VoiceTarget` 枚举项与前端下拉项
   （与连接页原有占位一致），状态 `preview`——架构就位但不可用。
2. **映射页语音 label**：统一为「语音输入」，不再写死 Win+H；
   实际唤起谁由连接页「识别方案」决定（后端 `action_label` 已改，前端常量已同步）。
3. **PTT 语义**：RC003 是按住传声、松手断流的硬件，「点一下开、不按着说、再点一下关」
   在硬件上不可行。因此任何识别目标都必须适配「按住说话」；第三方目标接入时按其
   真机能力决定 Release=松手停止 或 回落 Tap（只开不关，由应用/Esc 关闭）。
4. **不做方案 B（每键不同目标）UI**：当前单遥控器单语音用法不需要；架构上
   `ActionKind::Voice` 保持无参，将来如需再扩展，不影响现有配置。
