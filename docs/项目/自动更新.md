# 自动更新（Tauri v2 updater）

> 状态：代码已实现，随分支 `feat/auto-update` 提交；**发版后需按 §9 做一次真机验收**。
> 关联文档：`AGENTS.md` §9（打包与发版）、`.github/workflows/release.yml`、`CHANGELOG.md`。

## 1. 方案概览

使用 Tauri 官方 updater 插件做 Windows 自动更新（没有引入 WinSparkle 等第三方方案）：

1. 发布工作流在 GitHub Release 里上传带**更新签名**的 NSIS 安装包（`Remote.Mic_<ver>_x64-setup.exe.sig`）
   和静态清单 `latest.json`。
2. 应用启动后（仅正式构建）**立即异步检查一次**，运行期间每 30 分钟复查一次；两种自动检查
   都要求距上次成功检查 ≥1 小时才真正联网，手动点「检查更新」不受限制。检查时请求
   `https://github.com/poluce/windows-remote-mic/releases/latest/download/latest.json`。
3. 发现更高版本后，用户在「通用设置 → 关于与更新」点「下载并安装」：
   下载安装包 → 用配置里的公钥校验 minisign 签名 → 解压到临时目录并拉起 NSIS 安装器。
4. NSIS 以 `passive` 模式运行（`/P /UPDATE /R`）：显示一个进度窗口，安装完成后自动重启应用；
   因为安装模式是 `perMachine`，**每次更新都会弹 UAC**（未做 Authenticode，发布者显示「未知」）。
5. 应用在拉起安装器后会被 updater 直接 `exit(0)`，所以前端在下载完成时先调用
   `prepare_for_update_exit` 释放按键，避免虚拟 HID 残留按住状态。

检查到更新时侧栏「通用设置」会出现一个蓝点提示；更新状态只在
`src/store/updateStatus.ts` 维护一份，页面切换不会丢进度。

### 1.1 检查时机与频率

| 时机 | 行为 |
| --- | --- |
| 应用启动（窗口创建后初始化更新状态） | 立即异步检查一次，不延迟、不阻塞窗口显示 |
| 运行期间 | 每 30 分钟定时复查一次 |
| 实际联网门槛（启动 / 定时） | 距上次**成功**检查不足 1 小时则直接跳过，不发请求 |
| 手动「检查更新」 | 不受任何频率限制，立即检查 |

因此稳定状态下实际联网频率是：**启动时一次**（若距上次成功检查已超 1 小时）**+ 运行中约每小时一次**
（30 分钟 tick 里有一次会被 1 小时门槛挡掉）。「上次成功检查」时间持久化在 `config.json` 的
`last_update_check_at`（Unix 秒，0 = 从未检查），重启后门槛依然生效；检查失败不更新时间戳，
所以断网时每个 30 分钟 tick 都可能重试，直到成功。

## 3. 关键文件

| 文件 | 作用 |
| --- | --- |
| `src-tauri/tauri.conf.json` | `bundle.createUpdaterArtifacts = true`；`plugins.updater`（pubkey / endpoints / installMode） |
| `src-tauri/capabilities/default.json` | 前端调用 updater 命令需要 `updater:default` |
| `src-tauri/src/lib.rs` | 注册 updater 插件；`app_version`、`prepare_for_update_exit` 两个命令 |
| `src/store/updateStatus.ts` | 更新状态单一事实来源（phase / 版本 / 下载进度 / 错误文案） |
| `src/pages/SettingsPage.tsx` | 「关于与更新」区块：检查、下载安装、进度与错误提示 |
| `src/components/Sidebar.tsx` + `App.css` | 发现新版本时「通用设置」旁的小圆点 |
| `src/App.tsx` | 启动时初始化更新状态（正式构建会立即静默检查，运行中每 30 分钟复查） |
| `.github/workflows/release.yml` | 带签名的发布构建、校验 `.sig`、生成并上传 `latest.json` |
| `scripts/generate-updater-manifest.ps1` | 生成 `latest.json`（本地可单独测试） |
| `scripts/setup-updater-signing.ps1` | 生成/轮换签名密钥并写入 GitHub Secrets |

`plugins.updater` 配置：

```json
{
  "plugins": {
    "updater": {
      "pubkey": "<remote-mic-updater.key.pub 的内容，单行 base64>",
      "endpoints": [
        "https://github.com/poluce/windows-remote-mic/releases/latest/download/latest.json"
      ],
      "windows": { "installMode": "passive" }
    }
  }
}
```

- `pubkey` 必须是**公钥内容**，不是文件路径。
- `endpoints` 必须是绝对 URL；静态 `latest.json` 完全支持，不会自动追加任何参数。
- `installMode` 取值 `passive` / `basicUi` / `quiet`，默认 `passive`；本应用用 `passive`
  是因为 `perMachine` 安装反正要 UAC，`basicUi` 又不会自动重启。
- 不要设置 `requireSignedVersion: true`：当前发版用的 CLI 版本（2.11.x）签名里没有版本标记，
  打开后所有更新都会被拒绝。

## 4. 更新签名密钥

自动更新签名与 Windows 代码签名（Authenticode）是两回事：前者只用于校验更新包完整性，
不改变 SmartScreen / UAC 的「未知发布者」提示。

### 4.1 当前密钥

| 项目 | 内容 |
| --- | --- |
| 私钥 | `C:\Users\poluce\.tauri\remote-mic-updater.key`（**不要提交、务必备份**） |
| 密码 | `C:\Users\poluce\.tauri\remote-mic-updater.password.txt` |
| 公钥 | `src-tauri/tauri.conf.json` → `plugins.updater.pubkey` |
| GitHub Secrets | `TAURI_SIGNING_PRIVATE_KEY`（私钥文件内容）、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` |

> 私钥或密码丢失后**无法再签更新**；密钥轮换后，已安装的旧版本内嵌的是旧公钥，
> 自动更新会失败，只能让用户手动安装一次新版本。所以这两份东西必须备份。

### 4.2 重新生成 / 轮换

```powershell
# 生成新密钥（默认路径），输出公钥并把两个 GitHub Secrets 一起更新
powershell -ExecutionPolicy Bypass -File scripts/setup-updater-signing.ps1

# 轮换（会破坏已安装版本的自动更新，慎用）
powershell -ExecutionPolicy Bypass -File scripts/setup-updater-signing.ps1 -Rotate
```

生成后把脚本打印的公钥填进 `src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`。

### 4.3 本地构建

`createUpdaterArtifacts = true` 时，`npm run tauri build` 会要求签名密钥环境变量，
没有密钥会在打包最后一步报错。贡献者本地只想编译安装包时用：

```powershell
npm run tauri build -- --config '{"bundle":{"createUpdaterArtifacts":false}}'
```

要产出可用的更新包：

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = [IO.File]::ReadAllText("$HOME\.tauri\remote-mic-updater.key")
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = [IO.File]::ReadAllText("$HOME\.tauri\remote-mic-updater.password.txt")
npm run tauri build
```

注意私钥内容与 `.sig` 文件都不能带多余换行（base64 解码很严格）；签名脚本已经做过 `Trim()`。

## 5. 发布流程（在原有流程上增加的部分）

1. 版本号三处同步 + `CHANGELOG.md` 写入本次变更（**`latest.json` 的 `notes` 取自 CHANGELOG 对应版本小节**）。
2. 打 tag 触发 `Release Windows Build`：
   - 检测到 `TAURI_SIGNING_PRIVATE_KEY` → 带签名构建，产出
     `target/release/bundle/nsis/Remote.Mic_<ver>_x64-setup.exe` 与同名 `.exe.sig`；
   - 没有密钥 → 用 `--config` 关掉 updater 产物，只出普通安装包（并在日志里警告）。
3. 工作流自动生成 `staging/latest.json` 并连同 `.sig` 上传到 Release。
   Release 资产应包含：安装器、`remote-mic.exe`、`SHA256SUMS.txt`、`*.exe.sig`、`latest.json`。
4. 发版后核对：
   - `gh release view <tag> --json assets` 里 `latest.json`、`*.exe.sig` 都在；
   - `curl -L https://github.com/poluce/windows-remote-mic/releases/latest/download/latest.json`
     返回的 `version` / `url` / `signature` 正确，`url` 必须是**带 tag 的固定地址**；
   - 应用内「检查更新」能发现新版本。

> **每个正式 Release 都必须带 `latest.json`**：`releases/latest/download/latest.json` 指向最近一个
> 非草稿、非预发布 Release，一旦它缺少该资产，所有老客户端都会 404。

> 文件名注意：本地 Tauri 产出的安装包叫 `Remote Mic_<ver>_x64-setup.exe`（空格），而 GitHub Release
> 资产名会把空格归一化成点（历史产物均为 `Remote.Mic_<ver>_x64-setup.exe`）。发布工作流在收集产物时
> 主动把空格替换成点再生成 `latest.json`，保证清单里的 URL 与实际资产名一致；
> Windows 上手动验证时也要用归一化后的名字。

## 6. 本地测试

`tauri dev` 下 `check()` 可以正常工作（debug 构建允许 http endpoint），但**不要**在 dev 里执行
安装 —— 安装器会装进 `%PROGRAMFILES%` 并杀掉 dev 进程。

本次实现验证「发现新版本」UI 用的办法：

```powershell
# 1) 本地起一个静态更新服务（Windows 端）
python -m http.server 8787 --directory .\mock-updates

# 2) 用额外配置覆盖 endpoint，启动 dev
npm run tauri dev -- --config tmp-updater-conf.json
# tmp-updater-conf.json:
# { "plugins": { "updater": {
#     "endpoints": ["http://127.0.0.1:8787/latest.json"],
#     "dangerousInsecureTransportProtocol": true } } }
```

`mock-updates/latest.json` 里写一个比当前版本高的版本号即可验证 UI（签名只在真正下载时校验）。
端到端「下载→安装→自动重启」必须在**安装版**上验证：先安装基线版本，再发布/本地 mock 更高版本。
参考上游限制：updater 配置是在编译期写进二进制的，测试 endpoint 也要跟着重新构建。

## 7. 已知限制与风险

- **每次更新都弹 UAC**：`perMachine` 安装的 NSIS 安装包 manifest 要求管理员权限，
  passive / quiet 模式都免不了；拒绝 UAC 时 updater 会报错（2.12 的报错文案比 2.14 含糊）。
  上游 issue [#3000](https://github.com/tauri-apps/plugins-workspace/issues/3000) 讨论了
  perMachine 静默提权，目前没有落地。
- **未做 Authenticode 代码签名**：更新包本身有 minisign 保护，但 UAC/SmartScreen 仍显示「未知发布者」。
  代码签名是独立待办。
- **安装器会重跑 `hooks.nsh`**：更新时 `NSIS_HOOK_POSTINSTALL` 会再执行一次虚拟 HID 驱动安装。
  如果更新时 `WUDFHost` 正映射着旧的驱动 DLL，可能出现驱动文件被占用；**必须真机验收这一条**。
  安装器是提权运行的，所以不会再额外弹一次 UAC。
- **应用退出很突然**：updater 在 Windows 上是 `std::process::exit(0)`，不走 `RunEvent::Exit`；
  已用 `prepare_for_update_exit` 提前释放按键。日志是逐行落盘的，影响可接受。
- **安装器临时目录不清理**：上游 issue [#2132](https://github.com/tauri-apps/plugins-workspace/issues/2132)，
  每次更新会在 `%TEMP%` 留一份安装器副本。
- **旧版本第一次升级**：自动更新是本次才加入的，0.6.2 及更早版本没有 updater，
  用户需要手动安装一次带更新功能的版本，之后才能走自动更新。
- 便携版 `remote-mic.exe` 不参与更新（没有 bundle 标记，也没有签名），仍按手动替换处理。

## 8. 排查

| 现象 | 可能原因 / 处理 |
| --- | --- |
| 检查更新提示「更新服务暂时不可用」 | 最新 Release 缺少 `latest.json`，或网络/代理问题 |
| 提示签名校验失败 | `latest.json` 的 `signature` 与安装包不匹配；`signature` 带了换行；公钥/私钥不是一对 |
| 点了下载没有反应 | 看 `%LOCALAPPDATA%\RemoteMic\RC003\remote-mic.log`；确认 `TAURI_SIGNING_PRIVATE_KEY` 是否为空 |
| 安装时 UAC 被拒 | updater 报错，应用不退出；重试并允许管理员权限 |
| 更新后没有自动重启 | 检查 `installMode` 是否为 `passive`/`quiet`（`basicUi` 不会重启）；RDP 断开时没有 shell 会话也不会重启 |
| 更新后版本号没变 | 安装器可能失败（updater 观察不到安装器退出码）；看 Windows 应用日志后手动重装 |

日志里搜索 `[app]`、`updater` 关键字。最新 Release 的清单可以直接用浏览器打开
`https://github.com/poluce/windows-remote-mic/releases/latest/download/latest.json` 核对。
