# 问题记录：读取返回 / 音量+ / 音量- 按键信号

> 状态：✅ 已解决。返回键可连续、可靠读取；根因是 Rust 端 `in_grace()` 的 mutex 死锁（详见第 9 节）。
> 目标：可靠读取小米遥控器 RC003 的返回、音量+、音量- 三个按键信号。
> 背景：方向、OK、Home、Menu、Power、TV 等键可通过 Raw Input 正常获取；语音走 ATVV 正常。唯独这三个键被系统 HOGP 层过滤，普通应用无法直接收到。
> 最新结论：Frida 注入 WUDFHost 链路本身一直正常（hook 持续捕获、TCP 写链持续完成）；「只收到第一次按键」的假象来自 Rust 端 `serve_client` 线程在 `in_grace()` 处死锁，导致第一条报告之后的所有上报读不进来。修复后返回键连续按压正常。
> 追加结论（2026-09-01）：「吃掉」模式已在驱动层落定——真实写入点是 `0x20080` 的 memcpy 源缓冲区（GATT 通知 → 队列项 → WDF 请求缓冲区），钩该点清零后系统完全看不到按键（详见第 10 节）。
> 追加结论（2026-09-01 晚）：长按麦克风时看门狗会把「2 秒无 HID 报告」误判为松开，提前触发 Release → 第二次 Win+H 取消语音输入；已对麦克风 `0x3E` 禁用看门狗自动释放（详见第 11 节）。

## 1. 问题定义

### 1.1 按键通道

| 下 | `0x51` | 标准 HID → Raw Input | ✅ 可获取 |
| 左 | `0x50` | 标准 HID → Raw Input | ✅ 可获取 |

| 主页 | `0x4A` | 标准 HID → Raw Input | ✅ 可获取（vkey=36，已修复映射） |
| 菜单 | `0x65` | 标准 HID → Raw Input | ✅ 可获取 |

| TV | `0x35` | HOGP 旁路（标准 usage） | ✅ 可获取（实测 Raw Input/钩子看不到） |

### 1.2 根本障碍

- RC003 的返回 / 音量 / TV 键走 **HID-over-GATT（HOGP）**。
- Windows 的 `hidbthle.sys` 会先处理/过滤这些报告，普通应用通过 Raw Input / HID API 收到的信息已经被系统过滤。
- 要拿到原始报告，需要在系统过滤前截获，因此选择向 HOGP 宿主进程 **WUDFHost.exe** 注入 Frida Gadget。
- **注入本身已经打通**：Gadget 能加载、TCP 能连接、能捕获到返回键 `0x00F1`。
- **已解决**：连续按键只上报一次的根因是 Rust 端 `in_grace()` 的 mutex 死锁（详见第 9 节），与 Frida / HOGP / 系统去重无关。

### 1.3 信号通道澄清（重要实测结论）

- **usage 标准性**：
  - 音量+ `0x80`、音量− `0x81` 是 **HID 键盘页标准 usage**（Keyboard Volume Up/Down），不是非标准协议。
  - TV `0x35` 是 **HID 键盘页标准 usage**（Keyboard Launch Media Select）。
  - 返回 `0xF1` 是**厂商自定义 usage**（HID 键盘页 0xE8–0xFF 为保留区，小米自行使用）。
- **四个键在 Windows 里的命运完全相同**（都属于「应用命令类按键」）：
  - 系统**认识并原生处理**它们：返回 → `VK_BROWSER_BACK`（浏览器后退）、音量 → `VK_VOLUME_UP/DOWN`（系统音量变化）、TV → `VK_LAUNCH_MEDIA_SELECT`，走 WM_APPCOMMAND 应用命令通道（推断，待真机验证）。
  - 它们被 HOGP 层从「键盘输入通道」分流，所以 **Raw Input 和 WH_KEYBOARD_LL 钩子都看不到**（实测）。
  - 但 **Frida 旁路（HOGP 驱动层）四个键都能捕获到**（实测，日志可见 `0x00F1` / `0x0080` / `0x0081` / `0x0035`）。
  - 返回键**没有被系统丢弃**——它和音量/TV 键完全同类，只是 usage 编号是厂商自定义的。
- **主页键 vkey 映射（已修复）**：键盘页 `0x4A` 实测 Windows 映射为 `VK_HOME(36)`，不是 `VK_BROWSER_HOME(172)`。`usage_to_vkey(0x4A)` 已改为 36；消费类页 `0x0223` 仍映射 172（不同通道）。
- **双重处理问题**：系统原生执行（音量+1 / 浏览器后退）+ 旁路注入映射动作 = 一个信号做两件事。普通键（方向/OK/菜单等）同样存在此问题（系统原生 + Raw Input 注入）。现已由驱动层「吃掉」模式解决（见下，真机验证通过）。
- **「吃掉」模式（已实现并真机验证，默认开启，连接页可切换）**：真实报告路径是 **GATT 通知 → 8 字节队列项 → `0x1febc` 分配 WDF 请求缓冲区 → `0x20080` 的 memcpy 拷入 → 完成请求 → 内核 HID 驱动**。Frida 脚本钩住 `0x20080` 这个 memcpy 调用点：先把清零前的队列项原始报告转成 9 字节 IOCTL 格式（`01 00 00` + 3 个 usage）以 `gatt_read` 上报应用调度器，再把源缓冲区清零——系统 HOGP 层看不到任何遥控器按键，只由本应用注入映射动作。开关存于 `config.json` 的 `hid_tap_eat`（默认 `true`），后端写入 `%PROGRAMDATA%\RemoteMic\hid-tap\eat-mode.txt`，Frida 脚本每秒轮询热更新，切换无需重新注入。环境变量 `REMOTE_MIC_HID_TAP_EAT` 仅作开发兜底。
  - **旧方案（清 READ_CHARACTERISTIC_IOCTL 输出缓冲）已证明无效**：该 IOCTL 是报告处理完后的「补读」，输出缓冲区实测返回全零，不是系统消费的数据（详见第 10 节）。
  - 驱动更新导致偏移失效时，按 skill `hogp-report-path-re` 重新定位（`.agent/skills/hogp-report-path-re/SKILL.md`）。
- **已废弃的规划**：曾计划在 WH_KEYBOARD_LL 钩子里拦截普通键（return 1）实现「单一持有者」。驱动层 eat 生效后不再需要；且钩子层面无法区分遥控器与 PC 键盘（vkey+scan code 相同，实测会把 PC 键盘的静音键 173 也当遥控器键转发）。

## 2. 尝试过的方案

### 2.1 Frida HID Tap（注入 WUDFHost）—— 当前主方案

**思路**
- 用 Frida Gadget 注入到 HOGP 宿主进程（WUDFHost.exe）。
- Hook `NtDeviceIoControlFile`，在系统处理前截获 9 字节 HOGP 报告。
- 解析 usage：`0x00F1`=返回、`0x0080`=音量+、`0x0081`=音量-。

**已打通的部分**
- 注入成功：`LoadLibraryW` 能加载 Gadget，日志出现 `[hid-tap] 旁路服务已在运行`。
- TCP 连接成功：`127.0.0.1:17331` 保持 Established。
- 能捕获到返回键报告：
  ```text
  [DEBUG] [hid-tap] HOGP 原始数据: 9 字节, hex=010000F10000000000
  [INFO]  [hid-tap] HOGP 载荷 usage: 0x00F1
  ```

**当前未解决**
- 多次点击返回键，日志只出现一次 `0x00F1`。
- 已加诊断 JS：对所有输出长度 ≥ 9 的 `NtDeviceIoControlFile` 都上报（含非目标 IOCTL），但后续按键连诊断日志都没有。
- 可能原因：
  1. 遥控器/Windows HOGP 层对返回键只在状态变化时发一次报告，后续重复点击未产生新的 IOCTL；
  2. Frida hook 在第一次 `onLeave` 后失效（如 JS `writeChain` 卡住、Gadget 内部异常）；
  3. 返回键后续走了非 `NtDeviceIoControlFile` 的路径。

**部署要点（当前生效配置）**
- 运行时目录：`%PROGRAMDATA%\RemoteMic\hid-tap\`
- 目录 ACL：
  - SYSTEM（`*S-1-5-18`）：`(OI)(CI)F`
  - Administrators（`*S-1-5-32-544`）：`(OI)(CI)F`
  - Users（`*S-1-5-32-545`）：`(OI)(CI)M`（Modify，允许普通用户更新 JS/config）
- 注入时去掉 `\\?\` 前缀（`inject_into()` 内已实现）。
- DLL 保持官方名 `frida-gadget.dll`，config 同名 `frida-gadget.config`。

**对照实验结论**
- 曾怀疑必须把 DLL 改名为 `RemoteBridgeHidTap.dll` 才能成功（因为 Voice_VibeCoding 用了这个名字）。
- 实测证明：**重命名不是必要条件**。保持官方 `frida-gadget.dll` + `frida-gadget.config`，只要部署到 ProgramData 并设好 ACL，即可成功注入。

## 4. 实验记录（历史）

### 4.1 HidHide 详细实验记录（已废弃，保留备查）

**安装与重启要求**
- HidHide 需要手动下载安装包并安装，不是应用内自动安装。
- 官方安装包：`HidHide_1.5.230_x64.exe`（GitHub Releases）。
- 安装时以管理员身份运行，**安装完成后必须重启电脑**，驱动才会真正加载生效。
- 重启后确认：
  - 服务 `Nefarius HidHide Service` 状态为 `Running`
  - 驱动 `C:\WINDOWS\system32\drivers\HidHide.sys` 状态为 `Running`
  - `HidHideCLI.exe --version` 能正常输出

**设备实例路径会变化（重要）**
- 小米遥控器在 Windows 中的“设备名 / 友好名”不固定，本次连接后叫 **`MI RC`**。
- HID 设备实例路径（device instance path）不固定：
  - 重新配对遥控器后，`InstanceId` 末尾部分（如 `9&29512BC&0&0000`）可能变化。
  - 每次实验前用 `Get-PnpDevice` 按 VID/PID（`VID_012717&PID_32B8`）或 HID GUID（`00001812`）重新查询最新实例路径。
  - 不要硬编码设备实例路径。

**HidHide 操作记录（管理员权限）**
```powershell
# 查询 RC003 的 HID 设备实例路径
Get-PnpDevice -PresentOnly | Where-Object {
  $_.InstanceId -match 'HID\\\{00001812' -and $_.InstanceId -match '2717|32B8'
} | Select-Object Status,Class,FriendlyName,InstanceId

# 隐藏设备
$cli = "$env:ProgramFiles\Nefarius Software Solutions\HidHide\x64\HidHideCLI.exe"
& $cli --dev-hide "$devPath"
& $cli --cloak-on

# 确认
& $cli --dev-list
& $cli --cloak-state
```

**注意**
- 普通权限运行 CLI 会报 `Error code 0x0005 ... 拒绝访问`，必须用管理员 PowerShell 执行。
- `--dev-list` / `--cloak-state` 返回空或报错时，先确认是否用管理员权限运行。

### 4.2 其他替代路径实测（均不可行）

#### BLE GATT 直连 HID 服务（0x1812）

- 独立 Rust 探测程序，用 Windows BLE API 直接 `OpenAsync` HID GATT 服务。
- 结果：`GattOpenStatus(5)` = **AccessDenied**。
- 普通权限、管理员权限、SYSTEM（计划任务）三种上下文均失败。
- 结论：HOGP HID 服务被系统独占，应用无法绕过 WUDFHost 直接打开。

#### WinRT `HidDevice.FromIdAsync`

- 用 `Windows.Devices.HumanInterfaceDevice.HidDevice.FromIdAsync` 打开 RC003 HID 设备。
- 结果：返回 **null**（HRESULT 0），无法拿到设备对象。
- 结论：WinRT HID API 不暴露该 HOGP 设备。

## 5. 首次旁路成功后的衍生问题（已修复/处理）

> 以下问题都是在“Frida 注入成功、旁路能跑起来”之后陆续遇到的，属于集成/体验问题，不是注入本身的问题。

### 5.1 普通用户无法更新 ProgramData 里的 JS/config（拒绝访问）

**现象**
- 日志：`[hid-tap] 返回/音量旁路未启用：拒绝访问。 (os error 5)`。
- 原因：`%PROGRAMDATA%\RemoteMic\hid-tap\` 初始 ACL 给 Users 只有 `RX`（只读），普通用户进程想更新 `rc003-hid-tap.js` / `frida-gadget.config` 时被拒绝。

**修复**
- 把目录 ACL 中 Users 权限从 `RX` 提升为 `M`（Modify）。
- 当前 ACL：
  - SYSTEM：`(OI)(CI)F`
  - Administrators：`(OI)(CI)F`
  - Users：`(OI)(CI)M`
- 这样普通用户能更新 JS/config，SYSTEM 仍能读取/加载 DLL。

### 5.2 回退 LocalAppData 后 SYSTEM 又读不到 DLL（注入失败）

**现象**
- 曾尝试把运行时目录改回 `%LOCALAPPDATA%`（用户可写），结果日志：
  `LoadLibraryW 返回空（Gadget 未被加载）`。
- 原因：WUDFHost（SYSTEM）对用户目录访问存在不确定性/ACL 问题，注入再次失败。

**修复**
- 最终确定运行时目录仍使用 `%PROGRAMDATA%\RemoteMic\hid-tap\`。
- 同时给 Users `M` 权限解决写入问题，两边兼顾。

### 5.3 旁路频繁“连接已关闭，稍后重试”（读超时误报）

**现象**
- 日志每 2 秒出现一次：
  `[hid-tap] 旁路连接已关闭，稍后重试`。
- 原因：Rust 端 `serve_client` 设置了 **2 秒读超时**，而 Frida 脚本心跳间隔是 **5 秒**；没有按键事件时，2 秒内读不到数据就超时返回，误报连接关闭。

**修复**
- `serve_client` 改为**不设读超时**，完全依赖 Frida 心跳维持连接。
- 只有对端真正关闭时 `read_line` 才返回，避免误报。

### 5.4 “未连接”误报（语音桥重连误发 false）

**现象**
- 连接页显示“未连接”，但实际遥控器还连着。
- 原因：`start_voice_bridge` 外层循环在每次 `run_bridge` 返回后**无条件** `emit("ble-connection-status", false)`，把“语音桥本次会话结束/准备重连”误当成整条连接断开。

**修复**
- 删除外层循环里多余的 `emit(false)`。
- 连接状态只由 `run_bridge` 内部通过 `on_status` 在 BLE 真正连接/断开时推送。

### 5.5 切页后 ATVV 语音桥 / 旁路 / 端点状态变黄（本地 state 丢失）

**现象**
- 从连接页切到诊断页再切回来，`ATVV 语音桥`、`返回/音量旁路`、`ATVV 端点` 三个状态变黄（warn）。
- 原因：这些状态存在 React 组件本地 state，切页时组件卸载，state 重置为初始值。

**修复**
- 新增前端全局 store（`src/store/runtimeStatus.ts`），用 `useSyncExternalStore` 保存连接/桥/旁路/端点状态。
- 事件监听在 `App.tsx` 启动时全局注册一次，不随页面卸载销毁。
- 切页后从 store 恢复状态，不再变黄。

### 5.6 清空日志后实时行不显示（必须点刷新）

**现象**
- 点击“清空日志”后，继续按键测试，前端日志不实时出现；点“刷新”后才显示。
- 原因：`clearLogFile()` 把 `historyLoadedRef.current` 设为 `false`，之后实时事件到达时被当作“历史未加载”缓存到 pending，而不是直接显示。

**修复**
- 清空日志后把 `historyLoadedRef.current` 设为 `true`（历史已是最新空），后续实时行直接追加显示。

### 5.7 日志覆盖不全（被 raw_input 刷屏淹没）

**现象**
- 诊断页日志窗口看不到 `[hid-tap]` / `[bridge]` 等关键日志，满屏都是 `[raw_input] 键盘事件` / `[hook] 低层键盘事件`。
- 原因：前端直接读文件尾部 64KB，高频键盘事件把关键日志挤出窗口。

**修复**
- 前端诊断页**不再主动轮询读文件**，改为后端推送：

## 9. 最终排查过程与根因（2026-08-31）

> 本节记录「返回键只收到一次信号」的完整排查过程，以及最终定位到的死锁根因。

### 9.1 现象

- 旁路状态「已附着」（绿色），Frida 注入 + TCP 连接均成功。
- 第一次按返回键能收到 `0x00F1`，日志出现：
  ```text
  [DEBUG] [hid-tap] HOGP 原始数据: 9 字节, hex=010000F10000000000
  [INFO]  [hid-tap] HOGP 载荷 usage: 0x00F1
  ```
- 之后连续按返回键，日志再无任何新上报，心跳也消失。

### 9.2 排查过程（按时间顺序）

1. **怀疑 Frida 脚本「捕获所有 IOCTL 输出缓冲」卡死**
   - 当时脚本把 hook 放宽到「所有带输出缓冲区的 IOCTL」，`onLeave` 对每个 IOCTL 都 `readByteArray(args[8])`。
   - 假设：某些 IOCTL 的 `args[8]` 是 MDL/内核指针/已释放缓冲，读取时把 QuickJS 事件循环卡死。
   - 处理：收窄为「只 hook `READ_CHARACTERISTIC_IOCTL`、只在 `STATUS_SUCCESS` 且长度=9 时读取」。
   - 结果：**无效**，仍只收到一次。

2. **怀疑「队列 + 定时 flush」并发写坏 socket**
   - 当时上报用 `pendingLines` 队列 + 50ms 定时 `flushPending`，`writeAll` 不等待上一次完成。
   - 假设：并发 `writeAll` 把 socket 写坏。
   - 处理：改回串行 `writeChain`（每次 `writeAll` 排在上一次之后）。
   - 结果：**无效**，仍只收到一次。

3. **加文件诊断，绕过 TCP/事件循环**
   - 在 Frida 脚本里把 hook 统计直接写文件 `%PROGRAMDATA%\RemoteMic\hid-tap\hook-stats.txt`（`File.writeAllText`），并加 `writes_queued` / `writes_done` / `write_fails` 计数。
   - 关键证据：
     ```text
     {"calls":33,"captured":32,"success":32,"heartbeats":29,"writes_queued":29,"writes_done":28,"write_fails":0}
     ```
   - 结论：**hook 一直在捕获（32 次）、心跳一直在发（29 次）、写链一直在完成（28 次）、零写失败** —— Frida 端完全正常，是 Rust 端读不进去。

4. **在 Rust 端回调里加逐步日志**
   - 在 `serve_client` 加「收到消息 kind=…」日志，在 `raw_input` 回调加「回调进入 / on_vkey 完成 / 准备 emit / emit 完成」日志。
   - 发现日志停在「HOGP 载荷 usage」之后、`emit_usage` 的「特殊按键 usage」之前 —— 卡在 `on_ioctl_bytes` 的 `in_grace()` 调用处。

5. **定位根因：`in_grace()` 死锁**
   ```rust
   fn in_grace() -> bool {
       match *GRACE_UNTIL.lock().unwrap() {          // ① 拿到锁
           Some(until) if Instant::now() < until => true,
           Some(_) => {
               *GRACE_UNTIL.lock().unwrap() = None;  // ② 又去锁同一个 mutex！
               false
           }
           None => false,
       }
   }
   ```
   - `match` 的 scrutinee 拿到的 `MutexGuard` 会一直存活到整个 `match` 结束。
   - 当 800ms 宽限期已过、走到 `Some(_)` 分支时，在**还握着锁的情况下再次 `lock()` 同一个非重入 mutex** → 永久死锁。
   - `serve_client` 线程处理完第一条报告后卡死在 `in_grace()`，后续所有上报（心跳 + 按键）都读不进来。

### 9.3 修复

只锁一次，用 guard 直接改值：

```rust
fn in_grace() -> bool {
    let mut guard = GRACE_UNTIL.lock().unwrap();
    match *guard {
        Some(until) if Instant::now() < until => true,
        Some(_) => {
            *guard = None;
            false
        }
        None => false,
    }
}
```

### 9.4 经验教训

- 「只收到第一次」这类症状，先分清是**上游没产生**还是**下游没消费**。本次用「文件诊断 + 写链计数」证明 Frida 端一直在产出，才把矛头转向 Rust 端。
- 排查时不要只盯着最复杂的环节（Frida 注入 / HOGP / 系统去重），简单的 mutex 死锁同样能造成「只收到一次」的假象。
- `match *mutex.lock().unwrap() { ... }` 这种写法要警惕：guard 的生命周期覆盖整个 `match`，分支里再 `lock()` 同一 mutex 必然死锁。

## 10. 驱动层报告写入点逆向与「吃掉」模式落定（2026-09-01）

### 10.1 目标

实现「吃掉」模式：系统不响应遥控器按键，只由本应用注入映射动作。旧方案（清 READ_CHARACTERISTIC_IOCTL 输出缓冲）实测无效，需要找到系统真正消费报告的写入点。

### 10.2 真实报告路径（逆向结论）

```
遥控器按键
  → BLE GATT 通知到达 WUDFHost.exe 的 HOGP 驱动
  → 驱动把报告转成 8 字节队列项（2 字节头 + 3×u16 usage），放入环形队列
  → 处理函数 0x20720 取出队列项
  → 0x1febc 调 WUDFx02000.dll+0x1aab0 分配 WDF 请求缓冲区
  → 0x20080 的 memcpy 把队列项拷进请求缓冲区   ← 真正的写入点
  → WUDFx02000.dll+0xcd90 完成 WDF 请求（information=报告长度）
  → 内核 HID 驱动读取该缓冲区 → Raw Input / 系统响应
  → 处理完后驱动再发 READ_CHARACTERISTIC_IOCTL(0x80018483) 作为「补读」
```

- **`READ_CHARACTERISTIC_IOCTL` 不是报告来源**：它是报告处理完后的补读，输出缓冲区实测返回全零（GATT 通知已把特征值消费掉）。**清零它的输出缓冲永远无效**——旧 eat 失败的根本原因。
- 队列项格式（8 字节）与 IOCTL 输出（9 字节 = `01 00 00` + 3×u16）不同：上键队列项 `00 00 52 00 00 00 00 00` ↔ IOCTL `01 00 00 52 00 00 00 00 00`。

### 10.3 当前拦截实现

钩 `0x20080` 的 memcpy 调用点（只钩 call 指令，绝不钩 jmp thunk）：

1. 记录原始报告（追踪模式）；
2. 把清零前的队列项转成 9 字节格式以 `gatt_read` 上报应用调度器（应用照常注入映射动作）；
3. 清零源缓冲区（队列项），memcpy 自然把零拷进转发缓冲区 → 系统看不到按键。

真机验证（2026-09-01）：eat 开启后按「上」，系统无 `[raw_input]` 事件，日志出现「吃掉报告：已清零报告源缓冲区 len=8」，旁路连接稳定。

### 10.4 最终落定（2026-09-01）

- **默认开启 + 设置页开关**：`config.json` 的 `hid_tap_eat`（默认 `true`）；后端写入 `%PROGRAMDATA%\RemoteMic\hid-tap\eat-mode.txt`，Frida 脚本每秒轮询热更新，切换不弹 UAC、不重新注入。
- **应用侧闭环**：全部 13 键经旁路进 `KeyDispatcher` 映射表；麦克风默认 Press→Voice、Release→Voice（长按门控 PTT），普通键单击/双击/长按；长按只触发一次；长按阈值/双击窗口可设置。
- **看门狗**：自动释放兜底 2000ms（松开报告丢失时），带日志；**麦克风 `0x3E` 禁用自动释放**（长按由真实 HID release / ATVV AudioStopped 结束，见第 11 节）。
- 拦截关闭时旁路跳过 `0x3E`（麦克风由 Raw Input 投递），避免双路。

### 10.5 踩坑清单（详见 skill）

- 钩 ucrtbase 的 memcpy 抓不到驱动调用：API-set 转发器隔在中间，返回地址不在驱动模块。
- **钩 jmp thunk（0x28010 / 0x246d0）导致 WUDFHost fastfail 崩溃**（0xc0000409），应用反复弹 UAC。
- call 指令上挂 onLeave 不可靠；改为 onEnter 里清零 src。
- JS 发中文消息必须 UTF-8 编码，否则旁路 socket 报 `stream did not contain valid UTF-8` 断开重连。
- WDF 对象指针是编码指针：`~ptr & ~7` 解码，`+0x10` 有类型魔数 0x1003/0x1008。

完整方法论、关键偏移表、可复用代码模板与驱动更新后的重定位 Playbook 见 skill：`.agent/skills/hogp-report-path-re/SKILL.md`。

## 11. 长按麦克风导致 Windows 语音输入被取消（2026-09-01 晚）

### 11.1 现象

- 长按麦克风说话时，Windows 语音输入条（Win+H）中途被「取消/重置」。
- 日志显示一次长按内出现了两次 Win+H 注入：
  ```
  17:15:30.717  麦克风按下（0x3E）→ Press -> Voice（第一次 Win+H，打开/重置语音条）
  17:15:32.721  [hid-tap] 看门狗自动释放 usage=0x003E（松开报告丢失兜底）
                → Release -> Voice（第二次 Win+H）
  17:15:36.805  AudioStopped（真正的松手/停止推流）
  ```

### 11.2 根因

- RC003 长按麦克风时的信号行为：
  - 只在按下瞬间发一个 HID `0x3E` press 报告；
  - 长按期间**不重复发 HID 报告**，只持续推 ATVV 音频；
  - 松手时才发 HID `0x3E` release 报告 + ATVV `AudioStopped`。
- HOGP 看门狗的逻辑是「距上次 HID 报告超过 `AUTO_RELEASE_TIMEOUT`（2000ms）就判定松开报告丢失，自动补一个释放」。
- 麦克风长按超过 2 秒时，看门狗误判为「松开报告丢失」，提前触发 Release。
- Windows 语音输入语义（实测）：语音条已打开时再次按 Win+H **不会关闭弹窗，而是停止/重置当前输入会话**。
- 因此第二次 Win+H（看门狗提前触发的 Release）就是用户看到的「取消输入」。

### 11.3 修复

在 `crates/core-hid/src/tap.rs` 的看门狗 `ensure_watchdog()` 中，对麦克风兜底 usage `0x3E` **禁用自动释放**：

```rust
// 麦克风键是 PTT：长按期间遥控器不重复发 HID 报告，
// 只持续推 ATVV 音频；真正结束由 HID 松开报告或
// ATVV AudioStopped 负责。若按通用超时自动释放，
// 会在长按中把 Release 提前触发（Win+H 被二次按下
// 导致语音输入被取消）。因此对 0x3E 禁用看门狗兜底。
if usage == MIC_FALLBACK_USAGE {
    return true;
}
```

- 普通键仍保留 2000ms 看门狗自动释放兜底（防止 release 报告丢失卡键）。
- 麦克风长按改由「真实 HID 松开报告」或「ATVV AudioStopped」结束。

### 11.4 真机验证（2026-09-01 晚）

修复后一次约 5 秒长按的日志时序：

```
17:27:27.216  AudioStarted（遥控器开始推流）
17:27:27.217  HID 麦克风按下（0x3E press）
17:27:27.787  麦克风 Press -> Voice（长按阈值 550ms 后，第一次 Win+H）
   ↓ 持续约 5 秒音频解码
17:27:32.265  AudioStopped（遥控器停止推流）
17:27:32.267  HID 麦克风松开（0x3E release）
17:27:32.274  麦克风 Release -> Voice（第二次 Win+H，此时才停止/重置会话）
```

- 长按期间**不再出现** `看门狗自动释放 usage=0x003E`。
- Release 只在真实松手后才触发。
- 语音输入在长按期间不再被中途取消。
